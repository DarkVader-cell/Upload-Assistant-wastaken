# Discovery, screenshot intelligence, rules and seedbox planning

These are user-invoked preparation tools, not unattended submission or migration
workers. The existing CLI, tracker contracts, upload form, library, client
profiles and presets are unchanged. No external service, model or GPU is needed.
Use the normal authenticated Web UI; browser mutations require its CSRF token
and same-origin validation.

## Discover recorded candidates

Choose **Discover** in the application rail or **Discover candidates** in Library.

1. Browse an approved library directory in Upload first, or retain upload history.
   Browse results are remembered in the bounded browse index without an additional
   disk walk. Roots come from the existing configured browse roots, never from
   arbitrary discovery API input. No initial library crawl or live client query
   is performed. Existing indexed records can also be reused.
2. Open `/discovery` and select **Refresh recorded evidence**. This explicitly
   snapshots up to 2,500 recent history attempts and 2,500 indexed entries.
   Filtering and pagination use that in-memory snapshot, not the HDD. Refresh
   again after browsing more entries or changing history. The snapshot is not
   an exhaustive catalogue and disappears on server restart.
3. Select configured target trackers. Filter for no recorded success, never
   selected, or recorded failure, and any available metadata. Unknown metadata
   does not match a metadata filter. History currently projects category and
   resolution; codec/language/edition controls only match when actual projected
   evidence exists. Filenames are not silently promoted to metadata.
4. Inspect provenance, timestamps, blockers and ranking. Fresh unambiguous
   available sources rank first, then lower missing-metadata heuristic work,
   recorded outcomes, and path. Work units are **not measured preparation time**.
   Evidence older than seven days or undated is marked stale. Conflicting
   metadata is unknown. Stable canonical source identities deduplicate attempts.
5. Select at most 50 releases, **Preview selected preparation**, then confirm
   **Create reviewed queue**. Successful recorded targets are excluded; sources
   are revalidated. Follow **Review this queue in Upload**. This fills the normal
   form only; review paths, per-item arguments and settings before pressing Start.
   Existing queue overlap/path/argument checks remain in force. Issued queue
   links expire on server restart or if their content changes.

“No recorded success” is **not proof of remote tracker absence**. Capability,
search, edition/slot and seed evidence remain unknown until the normal workflow
verifies them. Discovery cannot upload anything. The legacy Library retry path
remains unchanged.

## Review screenshot signals

During an active screenshot review, select **Local quality signals / comparison**
from the Generated Screenshots panel. It opens a session-scoped contact-sheet
view at `/screenshot-intelligence?session_id=…`.

- Local thumbnails show brightness, near-black fraction, detail/edge proxies and
  perceptual near-duplicates within the same logical group. Compare suggested
  alternatives already present in that group. Signals are **heuristics**, not
  artistic judgements; dark scenes and soft focus can be intentional. Credits
  and text detection are **unknown**, not OCR.
- Remote-only images are listed as unknown; the server never fetches their URLs.
  Staged local replacements/additions are analyzed locally. Browser thumbnails
  are served from opaque session IDs with path confinement.
- Mark slots accepted/rejected/unreviewed. Decisions persist next to the review
  manifest and are bound to image identity/version; changed images become
  unreviewed. **Refill rejected slot** explicitly captures only that slot through
  the existing refill helper, keeping ID, ordering, group, target count and
  remote replacement semantics. Accepted slots are not batch-regenerated by
  this tool. Legacy manual review controls remain available and can intentionally
  replace images; acceptance is not a global immutable lock.
- Maximum 100 slots, 16 MiB and 16 million pixels per local image; animated or
  extreme-aspect inputs are rejected. A five-second per-report budget stops
  starting further image scores. Decode is serialized; an identity/version LRU
  holds at most 256 small results/thumbnails. No unchanged full-resolution
  rescoring is needed on reopening. Cancellation is checked between images by
  the analysis service; HTTP disconnect is not an execution cancellation signal.

No alternative frames are generated in the background. Explicit single-slot
refill uses the existing execution-owned capture/timeouts; there is no new
subprocess or remote-image retrieval path.

## Explainable preparation rules

Choose **Rules** or open `/automation-rules`.

1. Add named rules with priorities, enabled flags and **all** (AND) or **any**
   (OR) literal conditions. Fields: category, resolution, codec, language,
   edition, media_type. Operators: equals, in, contains. Matching is
   case-insensitive; contains is a substring, never a regex or expression.
2. Select tracker suggestions, an **existing** argument preset/client profile,
   or review requirements. Profile/preset names are references, not exported
   credentials or injected arguments. Requirements can add metadata review;
   screenshot review and torrent verification form an unconditional safety floor.
3. Choose a recorded candidate and preview draft rules. Every condition explains
   known/unknown metadata and provenance. Higher priority wins scalar conflicts;
   case-insensitive rule names break ties. Lists combine. Set an explicit
   per-release draft override if needed, preview, then save to persist it.
4. Save with optimistic revisions to prevent overwriting another editor's save.
   Import validates and replaces the saved schema only after confirmation.
   Export downloads the server-validated saved schema, not arbitrary draft data.

Rules **only propose** settings in this version. They do not automatically apply
presets/profiles, change implicit defaults, disable checks, transfer/delete,
queue, or submit. Copy confirmed choices into the normal Upload form. This is
intentional: no hidden submission hooks are installed.

State: `UA_DATA_DIR/data/automation_rules.json`, atomically replaced. Maximum
256 KiB, 32 rules, 32 conditions per rule, 500 release overrides. Unknown fields,
operators, actions or removed references fail closed. If a referenced preset or
profile is removed, restore its name before reloading/editing the saved rules.
No Python, shell, eval, regex or unrestricted CLI action is supported.

Example schema (references must exist in your app):

```json
{"version":1,"rules":[{"name":"Movies","priority":10,"enabled":true,"match":"all","conditions":[{"field":"category","operator":"equals","value":"MOVIE"}],"actions":{"requirements":["metadata-review"]}}],"overrides":{}}
```

## Plan seedbox placement or migration (read-only)

Choose **Planner** or open `/migration-planner`. Import a local JSON file or paste
snapshot JSON, then **Preview selected batch**. The incomplete example demonstrates
the import format but deliberately cannot produce readiness. Edit the candidates
array to choose the batch. Export downloads only the sanitized plan. No snapshot
is persisted by the server and no server path may be loaded through this API.

Evidence is operator-supplied, **not independently authenticated live status**.
Source, timestamps and age are visible. Evidence older than one hour or undated
blocks readiness. Maximum 2 MiB, 500 candidates, 100 related handoffs per
candidate, 5,000 inode entries per tree (subject to the total byte cap). Unknown
fields, credentials, executable commands, invalid hashes/capacities and future
non-finite timestamps are rejected.

The version 1 schema has `version`, `source`, `observed_at`, `destination`,
`candidates`. Destination has `id`, `role` (must be `grape`), `capacity_bytes`,
`used_bytes`, `pending_bytes`, `headroom_bytes`, `observed_at`, optional
`estimated_bytes_per_second`. Capacity minus usage, **other** pending transfers,
headroom and additional selected payload bytes determines shortage. Rate is an
operator heuristic, not a measurement. Missing values remain unknown.

Each candidate minimally requires `label`, exact `infohash` (40/64 hex) and
`size_bytes`. Optional evidence (missing values block completeness):

- `origin_kind`: `ua-original`, `direct-beyondhd`, `historical`, or `unknown`;
  `state`: `matched`, `recovery-required`, or `unknown`;
  `source_identity_matches`, `age_gate_passed`, `lifecycle_gate_passed` booleans.
- `own_destination`: `{destination_id, infohash, complete, seed_ready, verified_at}`.
  It must verify the original's **own exact infohash** on the selected Grape ID;
  a related tracker hash or same name/size is never a substitute.
- `related_handoffs_complete`: explicit boolean attesting the complete list;
  `related_handoffs`: verification objects in the same shape. Every handoff must
  verify complete and seed-ready on this destination. An absent/partial list
  is not proof that no handoffs exist.
- `tracker_hardlinks_remaining`: must be zero. `tree`:
  `{kind, complete, observed_at, entries:[{kind,nlink}]}`. Tree kind is `file` or
  `directory`; every entry must be `regular` with `nlink:1`. Directories require
  an exhaustive current tree attestation, including absence of symlinks/unusual
  objects. A single file needs exactly one regular-file entry. `symlink` and
  `other` entries explicitly block safety.
- Optional `payload_sha256`: a reliable canonical payload-content digest, **not**
  a filename/size hash (for directories, bind relative paths, sizes and every
  file's content). Equal digests and total sizes deduplicate transfer demand.
  Without this evidence, different infohashes with identical names/sizes count
  separately. Exact duplicate torrent candidates deduplicate; conflicts block.
- Optional `reuse`: `{destination_id,payload_sha256,size_bytes,verified,verified_at}`.
  Only matching current verified content identity/size on this destination
  reduces demand. Anything weaker remains a candidate reuse possibility.
  Reuse evidence never substitutes for the original's exact torrent registration.

Direct BeyondHD sources still require own exact-torrent verification and inode
checks; their separate ordinary UA lifecycle gate is not invented. A retained
`to_upload` tag is not itself a blocker once verified migration evidence exists.
Historical missing state requires the established explicit recovery workflow,
never inference from name/size. See [seedbox safety](seedbox.md).

“Evidence complete” means complete **planning evidence only**, never execution
permission. No transfer/deletion/action endpoint or executable command export
exists. This is not the remote Clementine worker and does not replace/deploy it.
Live snapshot exporters, client probes, SSH, transfer execution and worker
changes are deferred. GPU/OCR, background alternative generation and automatic
rule application are also deferred.

## Validation

Python tests use synthetic files, isolated state and mocked capture/clients.
DOM tests exercise selection, safe text rendering, preview, CSRF propagation and
non-execution. Run Node tests reproducibly with:

```sh
npm ci --prefix tests/ui --ignore-scripts
NODE_PATH="$PWD/tests/ui/node_modules" node --test tests/*.test.cjs
```

Source modules, templates, JS and CSS follow existing package-data globs and
Docker source inclusion. No runtime dependency constraint changed.
